## 1. Objective

0.0.0 is the **first version shaped like the whole idea and good enough to use
on real work**, not merely the first end-to-end slice. Two things make it that:

1. **Capability** — make it as good at hard tasks as the hardware and the
   engine allow before significant use.
2. **Packaging** — ship the **Core Pod OCI image** so the documented topology
   (ARCHITECTURE §3) is true and the system installs reproducibly on Linux and
   macOS (Apple Silicon first).

**Statistical validation moves to 0.0.x** (see §6). Measuring the loop's value
is most valid on the most complete system; the rigorous study runs against the
frozen 0.0.0, not a half-built one. The existing executable gates (G0–G6, the
security corpora, the process/recovery matrix) still run throughout.

## 2. Decisions

| # | Decision |
|---|---|
| D1 | 0.0.0 = **capability + Core Pod image**, accepting a longer runway. |
| D2 | "Better at hard tasks" targets **both** the `eval/bench` corpus (proxy) and real projects (the point). |
| D3 | Primary operator is the maintainer; **others soon** → the Core Pod image + deploy flow are in scope. Targets: **Linux + macOS, Apple Silicon first** (multi-arch `linux/arm64` + `linux/amd64`). |
| D4 | The Core Pod is one container running the single `athanor` daemon (core/gateway/scanner/ui are packages, not processes). It holds the Podman socket to spawn Job Pods; Job Pods never do ([ADR-0069](adr/0069-core-pod-packaging.md)). |
| D5 | **Statistical validation is 0.0.x.** The soak/quality run is endurance evidence (G7) and a baseline, captured after the freeze. |
| D6 | **Freeze rule:** 0.0.0 tags when the acceptance set in §4 is green and the docs are updated. Nothing tags before the freeze; nothing is added after it without a 0.0.x bump. |

## 3. Workstreams

### WS-A — Capability (M9-T1…T4)

The levers that actually move hard-task success, in priority order. Each has a
**verification edge** (the cognitive-regulation rule): an operation earns its
place only if a grounded signal can judge it.

| ID | Deliverable | Acceptance / evidence |
|---|---|---|
| M9-T1 | **Repair-on-test-failure loop** — bounded refinement that feeds the failing command's stderr and the unmet criterion back into a repair, re-verifies, and keeps the result only on a passing edge. Builds on M8-T11's `self_refine`. | A code candidate that fails tests is repaired and accepted without a human; the failing→repair→pass path is audited; the loop is bounded and cannot accept a non-passing artifact (G3 intact). |
| M9-T2 | **Model onboarding & qualification** ([ADR-0049](adr/0049-model-onboarding-qualification.md)) — enumerate available models, check feasibility, run a bounded per-role qualification (anchor + judge agreement for judges; a real-test code suite for generators), and propose a routing table for HITL approval. ML-free. | `athanor doctor`/Daydreaming proposes a per-role routing table from the locally installed models; the proposal is HITL-gated; a missing/weak model is reported, not assumed. |
| M9-T3 | **`data` deterministic verifier** — promote the probe's JSON-schema validator into `internal/verify`. | A `data` candidate is accepted/rejected by a schema check, not the judge; `media` stays judge-advisory and is documented. |
| M9-T4 | **Diversity + prompt/context polish** — enable bounded divergence re-rolls; surface the fixture/hidden-test contract to code generation. | Measured on the corpus as a proxy; no regression in cost bounds. |

### WS-B — Core Pod OCI image (M9-T5…T8)

## 4. The 0.0.0 acceptance set

Bounded, so "best" cannot be unbounded:

**Capability**
- M9-T1 lands and is demonstrably exercised on the corpus (a failed candidate is
  repaired and accepted).
- M9-T2 proposes a routing table from the locally installed models.
- M9-T3 gives `data` a deterministic verifier.

**Packaging**
- The Core Pod is the **only supported runtime**
  ([ADR-0078](adr/0078-core-pod-only-runtime.md)): the installer/`start` run it,
  the soak measures it, and the host binary is a client/dev tool.
- The image boots, answers `/healthz`, spawns a Job Pod, and tears it down; Job
  Pods provably never receive the Podman socket.
- Fresh-install demo < 15 min on Linux and macOS.

**First use**
- Onboarding proposes a routing table from a bounded qualification on the
  installed models (F2).
- The first project produces an approved plan artifact before work starts (F3).
- A completed job can be presented and reviewed, and the review is stored with
  provenance (F4). *Functional* is the 0.0.0 bar; first-class GUI polish is a
  1.0.0 goal.
- A night of shadow experiments produces a day-2 package with conclusions and
  samples; the operator confirms tested, **project-scoped** adjustments (F6).
- The digest is a persistent approval ledger (F6).

**Gates**
- `make check`, `make test-integration`, `go test ./internal/gate/` green.
- A sustained-load soak of the **Core Pod** on a **frozen corpus version** shows:
  no orphan pods, no unrecovered `kill -9`, bounded RSS/goroutines/WAL/disk, one
  human sleep/wake. A corpus version changes only at a major boundary
  (x.0.0 → (x+1).0.0).
- §31.3 audit checklist signed off; ARCHITECTURE §3/§32 match reality.

**Not required for 0.0.0:** statistical significance of the loop (0.0.x);
deterministic `media` verifier; the deferred capabilities in §7.

## 5. What the soak becomes

The warm-up already running is a **baseline snapshot on the pre-capability
engine** (it earned its keep by catching the synthesis defect, now fixed in
[ADR-0068](adr/0068-synthesis-keeps-passing-candidate.md)). It is **not** the
0.0.0 soak: the quality numbers will shift once M9-T1/T2 land. Endurance/recovery
evidence (G7) is captured **after the freeze**, on the real 0.0.0.

Long term ([ADR-0075](adr/0075-frozen-corpus-compass.md)) the **frozen
benchmark** is the controlled study across major versions; the soak is one run
shape of it (endurance), not the capability instrument:

- the **benchmark** = task set + procedure + **external scoring**, cut at
  **x.0.0** and never edited until **(x+1).0.0**;
- **sensitive to what we change** (especially the MCE): context-heavy tasks,
  multi-session memory scripts, and mechanism metrics (retrieval hit,
  context/KV, compaction, tokens, latency);
- the **headline** uses frozen external checks, never the engine's own
  verifier/judge; internal decisions are reported separately;
- run against the **Core Pod** (the shipped artifact);
- a **capability matrix** (screen → confirm) plus a **soak** (endurance); a
  smoke subset on engine-surface changes, full pre-tag; **not CI**, not a
  formal release gate;
- raw outputs retained so future benchmark versions can re-score old runs.

Real use feeds **selection** ([ADR-0076](adr/0076-continuous-evidence.md),
[ADR-0077](adr/0077-two-day-cycle.md)); the frozen soak **validates** it. Beta
use of 0.0.0 candidates starts **now**, before the freeze, as the primary design
and development signal.

## 6. Why validation waits for 0.0.x

Measuring a system you are still changing measures a moving target. The right
sequence is **build capability → freeze → measure**. The loop's value is the
question M8/F4 could not answer on an unfinished instrument; it deserves the
finished system. Meanwhile the *correctness* gates (containment, state machine,
recovery, security corpora) keep running, so deferring the *statistical* study
does not defer *safety*.

## 7. Out of scope (post-0.0.0)

Statistical significance (0.0.x); deterministic `media` verifier; skills runtime
+ `skill_refinement`; Browser Mode; cloud credential broker; Exploration Paths;
adversarial self-critique + tree search (M8-T12); full Statistics/Memory-Browser
views.

## 8. Risks

| Risk | Mitigation |
|---|---|
| "Best we can" is unbounded → 0.0.0 never ships | The §4 acceptance set + D6 freeze rule. |
| First-use scope creep | The bounded F1–F8 list and the §4 first-use set; anything else is 0.0.x. |
| Two runtimes drift; the soak measures the wrong artifact | [ADR-0078](adr/0078-core-pod-only-runtime.md): Core Pod only; host binary is client/dev. |
| Self-grading from IRL use | Two-axis approval ([ADR-0077](adr/0077-two-day-cycle.md)), the frozen soak as referee, and the judge never a label ([ADR-0076](adr/0076-continuous-evidence.md)). |
| Overnight experiments burn the budget or block on a human | Shadow-only, bounded, preemptible, HITL-free nights; human questions queued for the morning. |
| Nested Podman on macOS blocks "Core Pod only" | Prove socket path, named volumes, and Job Pod teardown before retiring the host path. |
| Core-Pod socket is a new attack surface | ADR-0069 trust split + a structural gate test + §31.3 audit. |
| Capability work regresses cost bounds | Corpus proxy + existing budget/verifier tests. |
| Model qualification is a large surface | ADR-0049 is ML-free (measurement + policy) and HITL-gated. |

## 9. Implementation order

See [first-use.md](first-use.md) Part D for the dependency-ordered list. In
short: Core Pod-only runtime → doctor fix → evidence reducer → derived labels →
shadow experiments → digest ledger → review queue/approval → onboarding →
project interview → presentation/notifications → budgets/issues/web → frozen
corpus v1 → installer/demo.

## 10. 1.0.0 direction

0.0.x validates; 1.0.0 completes. The pillars are in
[1.0.0-direction.md](1.0.0-direction.md): **first-class GUI (the main focus)**,
validated self-improvement, a mature benchmark, trustworthiness, complete
workflows, portfolio/multi-project, distribution, and efficiency. **First-class
GUI is a soft goal for 0.0.0** (a functional first-use flow) and the **main
focus of 1.0.0**.
